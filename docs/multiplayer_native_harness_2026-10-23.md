# Real two-client multiplayer observer

`tools/run_multiplayer_native.py` freezes the current checkout, refreshes imported resources, launches one local authoritative WebSocket server, and launches two separate native Godot applications through macOS LaunchServices. Each process has private preferences. The runner preserves the exact frozen source, manifests, commands, server/client logs, client viewport PNGs, client actions, authority snapshots, and comparison receipts. It terminates only processes with the exact private project paths belonging to that run.

The clients host/join a real room, agree its map, and use the ordinary network commands to purchase workers, military, buildings, age advances, and research; assign idle workers; gather/deposit; attack-move; and demolish/rebuild a paid House. Updated short-case policy waits for its foundation to finish before placing another building, keeps military selected during losses, and selects the House before demolition. Native result-to-menu return uses a viewport mouse click on the actual result button. Match setup and combat/economy commands are scripted controller/transport integration, not a claim of manual play or complete UI input coverage.

Examples from the repository root:

```sh
# Root coordinator owns native launches; use a new output directory each time.
python3 tools/run_multiplayer_native.py --scenario interrupt --map 0 \
  --timeout 110 --output output/multiplayer-native-2026-10-23/native-interrupt

# Sustained 1x match, continuous economy and repeated army replacement/combat.
# The normal server 30-minute limit ends it in a draw. Minimum wall time is
# measured from the started transport event to the terminal result event.
python3 tools/run_multiplayer_native.py --scenario sustained --map 0 \
  --minimum-wall 1800 --timeout 4200 \
  --output output/multiplayer-native-2026-10-23/native-sustained-plains

# Full ordinary objective ending; maps: 0 Plains, 1 River, 2 Woodland.
python3 tools/run_multiplayer_native.py --scenario match --map 1 \
  --timeout 2400 --output output/multiplayer-native-2026-10-23/native-river

# Explicitly separate accelerated headless policy tuning, never native evidence.
python3 tools/run_multiplayer_native.py --headless --tune-speed 3 \
  --scenario match --map 1 --timeout 470 \
  --output output/multiplayer-native-2026-10-23/headless-policy-tune-river
```

`--prepare-only` freezes/imports without launching; `--prepared` uses that exact candidate later. `--queue` exercises the old random public-matchmaking path instead of a room. It still uses the local server; it does not connect to the production service. By default all gameplay runs at 1x. The optional accelerated tuning flag is rejected for native and sustained sessions.

The source baseline is recorded after successful import and before game launch. `import-source-audit.json` preserves all pre-import hashes and the import delta; changes other than newly generated script `.gd.uid` metadata stop preparation. The final receipt compares against that post-import baseline. Native cleanup parses the full Godot executable path and exact private project path and records every signal in `cleanup.json`. Each client flushes PID, wall/UTC times, focus/close notifications, harness quit reasons, and finalization to its lifecycle JSONL. Close notifications are observed without suppressing ordinary window-close behavior. Result PNGs wait 0.5 seconds for the normal 0.4-second panel fade before the Menu click.

For short full matches, both scripted players fight away from the Sacred Site while developing their economies. After 650 game seconds, the host army moves to the Sacred Site and the guest army returns home, allowing a normal capture and natural Sacred victory. This is cooperative gameplay stress coverage, not a competitive balance benchmark. There are no grants, injected units, teleportation, injected damage, disabled production/combat, or forced result calls. The sustained case keeps fighting away from the objective and reaches the ordinary time-limit result.

Each client verifies its own loaded terrain against the received seed/archetype and compares every authoritative snapshot with the live replicas for HP, ownership, disabled simulation, owner bank, age, population fields, research, and resource depletion. The runner compares both clients' identical tick numbers: match/seed/grid identity, time, Sacred state, every jointly visible actor's public fields, shared visible resource remaining amounts, and terminal winner/reason. Enemy resource banks are intentionally private; the receipt does not pretend the players should have equal banks. The original sustained freeze has the earlier smaller comparison set (HP/owner/inert replicas/bank/age); source hashes distinguish this from later observer improvements.

Coverage gates require deposits, paid training/construction, visible enemies, real damage and unit losses, age progression, multiple technologies, a building loss, and result/menu return. Interruption deliberately closes the guest WebSocket without sending Leave and expects a connection-loss result on the guest and opponent-disconnect victory on the host. Supported lobby leave/rejoin and cancellation are covered independently by `tools/test_online_rooms.gd`; in-match resume is not supported. A report is only passing when both client witnesses finish, required coverage and comparisons pass, sources remain unchanged, and server/client logs contain no engine errors or warnings.

Snapshots and observers are bounded and read-only apart from their disclosed ordinary commands. No performance assertion is derived from these multiplayer runs, especially while other development processes run. Native phone-sized windows are desktop-rendered checks, not physical-phone tests. The final session report must state which frozen runs completed and their actual outcomes; the existence of this harness is not itself evidence that all scenarios passed.

## Native loading failure discovered during the loop

The first native River acceptance attempt (`output/multiplayer-native-2026-10-23/final-river/`) reached hosted room matching but both transports closed during scene loading before the first gameplay snapshot. It is a failed run, not a completed match. The runner did not initiate cleanup until the client failures had occurred. Client/menu file timestamps showed roughly 9–10 wall seconds around the blocked loading interval, while the old server log showed only 0.12 delta seconds of silence. Its network scripts were identical to the concurrently running Plains candidate; the menu difference was a presentation fade.

The multiplayer runtime investigator then reproduced two independent real-service failures: Godot's native WebSocket heartbeat timeout can close before reading an already queued Pong after a 5.6-second polling delay, and the server's former two-second result cleanup can discard a queued terminal result when a client resumes after a 4.2-second delay. The replacement uses application keepalive with a monotonic wall clock and acknowledges terminal delivery before closing, with a bounded legacy fallback. These reproductions explain concrete loading/result failure mechanisms; they do not establish that either was the user's unobserved historical crash.

Acceptance runs must use the replacement `network_session.gd` hash `692f19947b270efd88a9daab889d8ffc4443539055c285a2ea97a63b64b084b8` or a documented successor, and retain the earlier stopped/failed candidates separately. The latest witness also reserves age-up savings after its early combat phase so repeated casualty replacement cannot indefinitely prevent progression; it continues to buy all units, buildings, ages and upgrades normally.
